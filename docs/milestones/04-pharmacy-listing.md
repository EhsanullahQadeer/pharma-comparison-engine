## What we're building

The actual provider directory — getting real (or realistic pilot) pharmacies into the `Provider` table through two parallel routes:

1. **Manual** — a staff form to enter a provider by hand from verified public evidence.
2. **Automatic** — discovery jobs that pull candidate providers from official UK data sources into a review queue that promotes candidates to verified/published providers.

Per the roadmap, this explicitly does **not** mean auto-publishing scraped data — every first-time provider requires human approval (§4.2, step 3–4).

## How we're building it

- **Manual entry** — a Zod-validated Server Action form in the admin dashboard (M3a) that writes directly to `Provider` + `Evidence` with `status = discovered`; staff promote it through the state machine below.
- **State machine** (roadmap §4.2): `discovered → identity verified → ED catalogue verified → published → temporarily withheld / archived`. Modelled as a `status` enum on `Provider`; every transition is a deliberate staff action, never automatic for a first-time provider.
- **Automatic discovery** — client instruction (2026-09-16): free sources only, combined and deduplicated, with admin-configurable cadence per source rather than a fixed schedule. Built as `src/lib/discovery/adapters/*.ts`, one module per source behind a shared `DiscoveryAdapter` interface (`src/types/discovery.ts`), so adding a source doesn't touch review-queue logic:
  1. **Companies House** advanced search (real) — SIC 47730, incremental via `incorporated_from`. REST and streaming keys are *not* interchangeable; this slice only uses the REST key.
  2. **CQC API** (real) — its downloadable data includes website links, used as candidate domains; the only automated website-discovery signal in this slice.
  3. **NHS ODS** ORD API (real) — organisation IDs/status via Role RO182. FHIR R4/STU3 weren't used; ORD's list endpoint was the confirmed-stable contract.
  4. **NHSBSA Contractor Details** (real) — confirmed live against the real CKAN datastore API (`opendata.nhsbsa.net/dataset/contractor-details`); filters on `DISTANCE_SELLING_CONTRACTOR = "Y"`, resolves the current month's dataset resource dynamically since a new one publishes monthly.
  5. **GPhC premises data** (stub) — registration validation. Out of scope per the client's free-sources-only instruction (the paid Data Subscription Service isn't being purchased); the free register page also returned 403 during research review, so even a free-tier adapter isn't buildable yet without confirming a real access route.
  6. Provider websites / a public "suggest a provider" form — still not built; remains the main route to the actual ED offering, pricing and service details.
- Admin-configurable discovery scheduling (`DiscoverySource.cadence`/`enabled`) replaces the originally-planned fixed weekly job; `src/app/api/discovery/run/route.ts` self-selects which sources are due each time it fires, so the actual cron frequency (daily on Vercel Hobby, or more often on a paid plan) doesn't need to match any source's own cadence. Nothing auto-publishes — a discovered candidate only ever becomes/links a `Provider` via a staff click in the review queue, same rule as manual entry.
- **Identity resolution** — the full legal-entity/brand/domain/premises model from the original plan is still a flat `Provider` record (unchanged from M3a). What *is* built is `ProviderIdentifier`, a crosswalk table recording which external identifiers (company number, CQC location ID, ODS code, GPhC number) belong to which `Provider` — this is what dedup runs against, and it's exact-match only, never a fuzzy merge.

## Alternatives considered

| Approach | Trade-off |
| --- | --- |
| Custom — build catalogue records, permissions, staff forms in-app | Best validation/audit control; higher effort |
| Third party — structured CMS/database as the editorial backend | Faster staff tooling; relational integrity and exports need review |
| **Hybrid (recommended by roadmap)** — own the database, import staff-managed spreadsheets or CMS content through validation | Easy initial operations; mapping must be maintained |
